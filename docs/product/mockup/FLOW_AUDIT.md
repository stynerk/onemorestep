# 서비스 흐름과 데이터 갱신 점검

CTO Cap, 2026-11-13. HJ 요청에 따른 기술 점검이다. 소라가 최종 서비스 흐름·우선순위를 정리할 때 사용할 근거이며, 아래 제안이 구현됐다는 뜻이 아니다. 디자인 수정은 중단했고 제품 코드는 변경하지 않았다.

## 결론

현재 목업은 입력·저장·화면 이동과 일부 값 공유까지 동작한다. 회사 맥락이 바뀐 뒤 제안의 적합성·우선순위·준비 자료를 다시 판단하는 흐름은 없다. 페이지에 값이 보이는 것과 서비스 판단이 바뀌는 것을 구분해야 한다.

목표 흐름은 다음과 같다.

회사 정보·자료 확인 → 회사 맥락 갱신 → 관련 기회 재검토 → 변경 이유와 다음 행동 표시 → 준비 시작 → 진행·결과 기록 → 다음 제안에 반영.

현재는 회사 맥락 갱신 뒤 재검토가 빠지고, 진행·결과 기록도 상태 표시에서 끝난다.

## 브라우저 재현으로 확인한 핵심 사례

소스 5186fd8의 목업을 별도 로컬 주소(3110)에서 가상 입력으로 점검했다. 공개 사이트의 사용자 입력은 변경하지 않았다.

1. 지원 카드의 초안을 저장했다.
2. 업무 지도 목표를 ‘자금 확보 대신 고객 검증에 집중’으로 수정했다.
3. 브리핑 목표와 지원 카드의 연결 문구는 바뀌었지만 카드 3개의 제목은 모두 이전과 같았다.
4. 지원 상세의 연결 이유는 새 목표였지만 저장 초안은 이전과 동일했다. 초안이 오래된 기준을 사용한다는 경고는 없었다.
5. 지역을 ‘다른 지역’으로 답하니 불일치 안내는 표시됐지만 해당 지원 카드가 계속 홈에 남았다.

관심 주제·일정·반복 업무의 판단 미연결은 코드에서 확인했다. work-map.js는 해당 목록을 저장·표시하며, 카드 생성은 interactive.html의 고정 cards와 필터를 사용한다. knowledge.js는 선택 테마의 원문과 발췌를 붙인다. 실제 분석·추천 엔진은 없다.

## 우선 수정 순서(소라 검토용 추천안)

1. **하나의 상태와 갱신 규칙부터 정한다.** 회사 프로필·확인한 자료·기회·준비 작업·실행 이력을 구분하고, 어느 입력 변경이 어떤 결과를 다시 계산하게 하는지 정의한다. 화면마다 따로 값을 고치지 않는다. 현재 정적 목업에서 먼저 규칙 기반으로 검증할 수 있다.
2. **조건 변경에 따른 카드 변화를 끝까지 연결한다.** 목표·지역·등록 상태를 바꾸면 같은 외부 후보라도 채택/확인 필요/제외와 이유가 달라져야 한다. 준비 중인 작업을 조용히 삭제하지 않고 변경 경고를 남긴다.
3. **저장 초안의 기준 변경을 관리한다.** 작성에 사용한 회사/자료 버전과 현재 버전을 비교해 ‘재검토 필요’를 표시한다. 사용자 편집을 덮어쓰지 않고 새 초안을 별도로 만들어 비교하게 한다. 모든 수정이 모든 초안을 무효화하지 않도록 의존 항목을 기록한다.
4. **일정·진행·결과를 한 작업으로 연결한다.** 준비 시작에서 만든 작업의 마감을 지도와 브리핑에서 공유한다. 완료·보류 시각과 이유/결과를 기록하고 후속 제안에 쓴다. 수동 일정은 외부 공고의 마감처럼 취급하지 않는다.
5. **같은 흐름에 실제 Liner 조사·판단을 붙인다.** 데이터 연결이 검증된 뒤 조사 결과를 교체한다. API 성공 자체를 회사 맥락에 따른 판단 갱신의 증거로 삼지 않는다.

‘표시 갱신’, ‘판단 재검토 필요’, ‘재검토 중’, ‘재검토 완료/실패’를 화면에서 구별해야 한다. 회사 정보가 바뀌자마자 실제 외부 조사가 완료된 것처럼 표시하지 않는다. 요청 도중 입력이 다시 바뀌면 이전 입력으로 나온 응답이 최신 결과를 덮어쓰지 않게 한다.

## 기능 완료로 볼 검증 기준(제안)

- 목표를 자금 확보→고객 검증으로 바꾸면 카드/행동 또는 채택 이유·우선순위가 실질적으로 달라진다. 바뀌지 않았다면 그 이유를 설명한다.
- 지역이 지원 조건과 다르면 추천 상태가 바뀌고, 준비 중인 항목에는 조건 변경 경고가 남는다.
- 자료를 수정/삭제하면 상세 근거가 갱신되고 관련 저장 초안만 재검토 대상으로 표시된다. 사용자 편집은 유지한다.
- 한 작업의 마감을 바꾸면 지도·브리핑·준비 목록 모두 같은 날짜를 보인다.
- 완료한 작업은 실행 이력에 남고 다음 찾기에서 같은 행동을 새 제안으로 중복 권하지 않는다.
- 새로고침 후에도 변경 기준·작업 상태·이력이 일치하고, 재검토 실패 시 이전 결과와 실패 상태를 구분한다.

현재 목업은 이 기준을 통과하지 않았다. 화면 클릭·저장 검증을 서비스 루프 검증으로 보고한 범위를 바로잡는다.

## PM이 정할 것

최소 데모를 ‘목표/지역 변경 → 카드 판단 변경 → 준비 작업·초안 재검토’ 한 흐름으로 우선 묶는 것을 추천한다. 반복 업무의 실제 실행, 외부 자동 동기화, 정시 알림은 별도로 우선순위를 정한다. 화면 추가와 디자인 보완은 이 흐름을 검증한 뒤 진행한다.
