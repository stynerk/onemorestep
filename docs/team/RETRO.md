8. **시연과 검증은 재현 가능한 입력으로 한다.** 시연 완료 조건은 착수 전에 재현 가능한 시드와 기대 결과로 남긴다. 반복 QA와 녹화는 저장 모드를 기본으로 하고, 실호출 검증에는 별도 호출 예산을 둔다. 녹화와 평가는 사용한 커밋과 실행 모드를 기록한다. (Cap 개선)

## HJ 팀 회고 (2026-11-26)

### 1. 잘했던 점

### 2. 아쉬웠던 점

### 3. 개선할 점

- 다음 프로젝트부터는 개요를 명확하게 잡고 기획서를 구성하면서 성공 지표(마일스톤)를 제대로 설정하고 시작한다.
- 에이전트 구조를 더 세분화해 사업, 챌린저 등의 서브에이전트를 더 구성한다.
- AI가 짜 준 내용은 밸류 측면에서 이해가 안 되거나 와닿지 않는 경우가 많았다. 목표 밸류를 명확하게 제시하고 그것을 개선하도록 얼라인한다.
- Liner 크레딧을 $200 받았는데 실제로는 약 $4를 썼다. 리소스를 방치한 느낌이라, 기획 때부터 활용할 수 있는 리소스를 최대한 쓰도록 에이전트들과 충분히 상의한다.

## 개발PM Cap 회고 (2026-11-26)

Cap이 dev 스레드에 쓴 회고를 HJ가 전달했다. Cap은 읽기 전용 세션이라 기존 문서와 최종 QA 기록을 대조하지 못했다고 밝혔다.

### 1. 잘했던 점

- Liner 실호출과 저장 모드를 분리해, 외부 API 상태와 비용에 영향을 받지 않고 판정 로직을 반복 검증할 수 있게 했다. 실호출 연동과 저장 데이터 재현에 각각 확인할 기준을 둘 수 있었다.
- 판정 엔진을 30건의 기대 결과와 대조한 덕분에 일치율 25/30에서 어긋난 다섯 건을 특정했다. 딜러 추천도 '결과를 한 번 입력하면 1·2순위가 뒤집힌다'는 장면 단위의 완료 조건으로 바꿔, 시연에서 무엇을 확인해야 하는지 분명히 했다.

### 2. 아쉬웠던 점

- 저장 시드에 '검색은 정상적으로 끝났지만 결과가 없었다'는 근거가 빠져 다섯 건이 무효 대신 애매로 남았다. 딜러 추천도 결과 입력 전후의 순위 변화를 재현할 시드가 뒤늦게 요구됐다. 두 사례 모두 개발PM이 시연에 필요한 입력과 기대 결과를 구현 전에 완료 조건에 넣었어야 했다.
- Tony 검토 뒤 여러 PR이 멈췄고, 테스트 메일 Issue는 실제 진행 단계와 라벨이 어긋났다. 엔진과 추천 PR의 병합이 화면 작업의 선행 조건이었으므로, 검토 직후 각 PR에 남은 QA와 담당자를 개발PM이 명확히 잡았어야 했다.

### 3. 개선할 점

- 시연 장면마다 시작 시드, 사용자 입력, 기대 결과를 구현 착수 전에 한 줄씩 적는다. 저장 모드에서는 '정상 응답·0건'과 '호출 실패'를 별개 사례로 검증하고, 딜러 추천은 화면에서 결과를 입력한 뒤 실제로 순위가 바뀌는지 확인한다.
- 리뷰가 끝나면 PR에 다음 담당자와 남은 QA를 바로 적고 Issue 라벨을 맞춘다. 화면 작업을 막는 선행 PR은 병합 순서와 최신 main 기준 재검증 여부까지 기록한다.
- 실호출은 QA에 필요한 시나리오와 호출 예산을 먼저 정하고, 성공 응답은 시드로 보관해 반복 검증에 쓴다. 녹화와 Gemini 평가는 같은 커밋과 시드를 입력으로 삼고, 결과에 커밋과 실행 모드를 남겨 재촬영이나 재평가 결과를 비교할 수 있게 한다.
