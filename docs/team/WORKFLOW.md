# 작업 흐름

개발 작업의 원장은 GitHub Issue다. 관문과 비개발 작업은 구글 드라이브의 팀 로그 시트에서 관리한다.

## Discord와 GitHub의 역할

| | Discord #onemorestep | GitHub |
|---|---|---|
| 하는 일 | HJ와 에이전트의 논의, 상태 질문, 결정 | 작업 인계, 구현, 검토, 기록 |
| 소라(PM) | HJ와 기획을 논의하고 결정을 받는다 | Issue를 쓰고 `@codex`로 Cap을 부른다. PR을 검토한다 |
| Cap(CTO) | HJ나 소라의 기술 질문에 답한다 | Issue를 받아 구현하고 PR을 연다 |
| 알림 | 웹훅(onemorestep_dev)이 GitHub 활동을 옮겨 온다 | |

규칙:

- Discord에서 정한 일은 소라가 Issue로 옮긴 뒤에만 실행된다. Discord 메시지로 Cap에게 구현을 맡기지 않는다.
- 작업 인계의 상세 내용과 결과는 Git 문서, Issue, PR에 남긴다. Orca 연결을 사용할 수 없으면 이 채널의 명시적 멘션으로 상대에게 협의를 요청한다(HJ 지시, 2026-11-12).
- 봇은 웹훅 알림과 자기 메시지에 답하지 않는다. HJ가 맡긴 작업에 관한 상대 에이전트의 명시적 협의·검토 요청에는 답할 수 있다. 멘션 ID는 실제 연결 확인 없이 추정하지 않는다.
- Discord에서 나온 결정은 소라가 팀 로그 시트(G_누적규칙 또는 백로그)에 남긴다.

## Issue 상태 (라벨)

| 라벨 | 뜻 | 다음에 움직이는 쪽 |
|---|---|---|
| `ready` | PM이 작업 지시를 다 썼다 | CTO |
| `in-progress` | CTO가 작업 중이다 | CTO |
| `review` | PR이 열렸고 검토를 기다린다 | PM |
| `changes-requested` | PM이 수정을 요청했다 | CTO |
| `owner-decision` | HJ의 선택이 필요하다 | HJ |

한 Issue에는 상태 라벨을 하나만 둔다. 상태를 바꾸는 쪽이 라벨도 바꾼다.

## 흐름

1. PM이 Issue 템플릿으로 작업 지시를 쓰고 `ready`를 붙인다.
2. CTO가 `in-progress`로 바꾸고 브랜치를 만든다. 브랜치 이름은 `issue-번호-짧은-설명`이다.
3. CTO가 구현하고 완료 조건을 직접 돌려 확인한 뒤 PR을 연다. PR 본문에 다섯 줄 기술 보고를 쓰고 Issue를 `review`로 바꾼다.
4. PM이 완료 조건을 기준으로 검토한다. 통과면 승인하고, 아니면 고칠 항목을 적고 `changes-requested`로 바꾼다.
5. 수정은 같은 브랜치와 같은 PR에서 한다. 새 Issue나 새 PR을 만들지 않는다.
6. PM 승인이 나면 `main`에 병합한다. 병합은 되돌릴 수 있으므로 HJ의 승인을 기다리지 않는다. 크리티컬하지 않은 병합은 소라와 Cap이 논의해 정한다(HJ 지시, 2026-11-12). 배포, 비용, 저장소 공개에 영향이 있는 병합만 HJ에게 올린다.
7. 소라와 Cap은 같은 작업 폴더에서 동시에 커밋하지 않는다. 소라는 별도 작업 트리(`git worktree`)에서 문서를 고친다.

## HJ가 직접 하는 것

- 관문 세 개: 컨셉 확정, 데모 시나리오 확정, 최종 제출
- 배포, 유료 서비스 가입, 결제, 저장소 공개 전환
- `owner-decision` 라벨이 붙은 Issue의 선택. Issue에는 선택지와 추천안이 적혀 있다.

## 규칙

- `main`에 직접 커밋하지 않는다. 문서만 바꾸는 경우는 예외로 한다.
- 하나의 PR은 하나의 Issue만 다룬다.
- 같은 Issue를 두 세션이 동시에 잡지 않는다. `in-progress`가 붙어 있으면 다른 Issue를 고른다.
- PR이 작을수록 검토가 빠르다. 하루 안에 끝나지 않는 Issue는 PM에게 나눠 달라고 요청한다.
